# Боевой контекст разработчика

`--combat JSON` добавляет явные изменения состояния к результату базового расчёта. Это интерфейс проверки модели; игрок не должен вручную составлять такие файлы. Продуктовый импорт должен заполнять подтверждённые поля автоматически и показывать пробелы покрытия.

Полный синтетический пример: [`examples/combat.json`](../examples/combat.json). В результате сохраняется его копия `combat.json`, исходные условия, последовательность множителей и независимое сравнение с замером. Все числовые проценты задаются долями.

Обязательные поля:

| Поле | Значение |
| --- | --- |
| `reference` | Состояние, уже учтённое в исходной панели |
| `target` | Состояние, которое рассчитывается |
| `tick_frequency` | `null` для непрерывной скорости с пределом 30 или `30` для неподтверждённой в SS14 гипотезы округления интервала |
| `armor` | Неотрицательная броня монстра, до пробивания |
| `nonphysical` | Булево значение: применять ли базовые 60% редукции брони, когда явная эффективность не задана |
| `missing` | Массив неизвестных или неучтённых эффектов |
| `notes` | Массив объяснений выбранного сценария |

Каждое состояние содержит ровно три массива: `damage`, `cast`, `taken`. Каждая строка массива содержит `id` уникального экземпляра, `affix` общей группы, `value`, целое неотрицательное `stacks` и `mode`: `add` или `multiply`. Повтор одного affix в режиме `add` складывается, разные affix перемножаются; `multiply` разрешён только при явной соответствующей семантике источника. Совпадение названия характеристики не доказывает одинаковую группу affix. Идентичные экземпляры внутри массива отклоняются.

Сначала рассчитываются отношения `damage(target)/damage(reference)` и `taken(target)/taken(reference)`. Скорость из панели умножается на отношение cast, затем ограничивается и при явном выборе округляется до тиков; к DPS применяется отношение полученной частоты к исходной ограниченной частоте. Нулевой исходный множитель нельзя использовать как делитель. Броня цели применяется один раз после этих отношений.

Наличие строки в `missing` не добавляет к урону коэффициент. Контекст не выводит стаки Heat из ёмкости магазина, не определяет uptime проклятий и не подтверждает наследование модификаторов Tangle. Статические вещи и поддержки, уже включённые в панель, не добавляются заново. `condition.taken` и боевой слой `taken` должны описывать разные изменения; их смысл требует подтверждённого исходного состояния.

Результат остаётся условным даже при пустом `missing`. Автоматическая сборка этого контекста из полного билда — отдельная незавершённая задача.

## Явная гипотеза пробивания брони

Необязательные поля `armor_effectiveness`, `armor_penetration` и `armor_penetration_order` задаются только вместе. Отсутствие всех трёх сохраняет прежний расчёт: броня монстра с базовой эффективностью 100% для Physical либо 60% для non-Physical, без пробивания. Частичный набор и явно заданные `null` отклоняются.

`armor_effectiveness` — итоговая применимая эффективность `E` в пределах 0–1, а не прибавка к базовым 60%. `armor_penetration` — доля `P` в пределах 0–1 либо точная строка `"panel"`, выбирающая импортированное `panel.armor_penetration`. При выборе `"panel"` отсутствие показателя вызывает ошибку. Если показатель присутствует в панели, явное числовое `P` обязано с ним совпадать; без показателя число разрешено только как явный сценарный вход разработчика. Булевы и бесконечные значения не принимаются.

Для `M = min(0.8, A/(0.9*A+30000))` реализованы обе условные формулы:

| `armor_penetration_order` | Итоговая редукция | Множитель урона |
| --- | --- | --- |
| `after_effectiveness` | `M*E−P` | `1−(M*E−P)` |
| `before_effectiveness` | `(M−P)*E` | `1−((M−P)*E)` |

Редукция может стать отрицательной, поэтому множитель урона может превышать единицу. Порядок **обязателен и не подтверждён**: наличие значения в сценарии не устанавливает игровую механику. Он остаётся в `combat.missing` и объяснениях результата. Выбирать порядок по совпадению с замером нельзя. Правила и остающиеся вопросы: [проверка Help](research/help-defense-conversion.md).

Пример дополнительных полей для сценария с автоматически импортированным пробиванием:

```json
{
  "armor_effectiveness": 0.6,
  "armor_penetration": "panel",
  "armor_penetration_order": "after_effectiveness"
}
```

Это дополнение к обязательному контексту, не полный JSON. Исходный selector сохраняется в копии контекста; результат содержит выбранный порядок, числовое пробивание и `armor_penetration_source`. Trace показывает число и его источник отдельно от единственного итогового множителя брони. Эффективность и броня цели остаются явными условиями, их нельзя восстанавливать по DPS манекена.

## Состояния Heat для Carino

Необязательный объект `carino` принимает явные `rank` свойства Incinerated Glory (1–5), `eternal` (булево) и состояния `reference` / `target` с целыми `heat` и итоговым множителем эффективности `effect`. Пример — [`examples/carino-combat.json`](../examples/carino-combat.json). Он компилирует проверенные коэффициенты свойства в обычные additive стеки и применяет отношение двух состояний через тот же расчёт. Добавлять эти же Heat-модификаторы вручную в массивы damage/cast повторно нельзя.

Максимум Heat, эффективность Burning Red, расход патронов и uptime из этих полей не выводятся. Наследование Heat модификаторов Tangle автоматически остаётся в списке неподтверждённых механик. Значения примера вымышлены; уровни свойств должны в будущем поступать от импортёра, а не из обязательной анкеты игрока. Источники коэффициентов: [формулы Carino](research/carino-combat-formulas.md).

Поле `validation` в JSON содержит исходные `predicted`, `measured`, разность `difference`, относительную ошибку `relative_error` и диагностическое отношение `measured_to_predicted`. При нулевом знаменателе соответствующее отношение равно `null`. Эти величины не участвуют в вычислении урона; даже совпадение не доказывает полноту модели.
