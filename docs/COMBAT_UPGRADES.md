# Сравнение полных условных боевых сценариев

`damage_lab.combatupgrades.evaluate(document)` сравнивает полные замены сценария
[`rawcombat`](RAW_COMBAT.md) при одной цели и одном uptime. Цена и валюта задаются
вызывающей стороной. Модуль не читает файлы, не обращается к рынку и не извлекает
модификаторы из импорта.

Это отдельный слой от [`rawupgrades`](RAW_UPGRADES.md): здесь величина сравнения —
полный условный боевой DPS после topology, Cold defence, явной модели брони,
increased/more damage taken и uptime. Вложенный `rawcombat` владеет каждым из этих
этапов. Comparator только вычитает два результата и рассчитывает ценовые отношения.

## Входной контракт

Объект содержит ровно четыре поля:

```python
{
    "format": "tli-combat-upgrade-scenario-v1",
    "baseline": complete_rawcombat_scenario,
    "currency": "synthetic tokens",
    "candidates": [
        {
            "id": "replacement",
            "name": "Synthetic replacement",
            "scenario": complete_replacement_rawcombat_scenario,
            "cost": 17,
            "missing": [],
        }
    ],
}
```

`baseline` и каждый `scenario` проходят публичный `rawcombat.evaluate` со всеми
его строгими проверками, source gates, списками неизвестных эффектов и числовыми
границами. Неизвестный эффект следует записать в `missing`; неизвестный или
конфликтующий gate остаётся таким в полном сценарии. Частичные объекты не заменяют
недостающие числа нулями.

Для всех вариантов полностью совпадают `target` и `uptime`, включая Cold
penetration, модель и penetration брони, increased taken и полный список more taken.
Списки сравниваются вместе с порядком и идентичностями строк. Также совпадают
`spell.context.skill_id`, `spell.context.catalog_sha256`, `spell.damage.roll_model`
и `spell.casting.frequency`. Несовпадение вызывает `ValueError`, даже когда один из
сценариев заблокирован. Для сравнения разных целей нужны отдельные вызовы.

Вложенный rawspell может сохранять неизвестные целые группы. Общие
`damage: null` либо `casting: null` с обеих сторон остаются blocked, без
числового прироста или ценового рейтинга. Одностороннее отсутствие такой группы
отклоняется как неподтверждённая общая roll/tick policy. HTML отличает неизвестную
группу скорости от явно выбранного `frequency: null`; target и uptime при этом
по-прежнему полностью обязательны и одинаковы.

Пулы урона, crit/cast параметры, source hash, effective level и topology могут
отличаться внутри полной замены с собственными gates. Старые пулы не прибавляются
к новым. Модуль не выбирает уровень, topology или подтверждённость автоматически.
Подтверждённые вызывающей стороной gates остаются условием модели; они не доказывают
runtime identity, свежесть состояния или фактический DPS персонажа.

У кандидата ровно пять полей: `id`, `name`, `scenario`, `cost`, `missing`.
`id` уникален. `id`, `name`, `currency` и строки `missing` — непустой обрезанный
текст длиной до 1024 символов. `candidates` и каждый `missing` — JSON-списки до
1000 элементов. Это ограничения интерфейса, а не ограничения игры.
`cost` — конечное число не меньше нуля или `null`; bool не принимается.
`0` означает явно бесплатную замену, `null` — неизвестную цену.
Метаданные каждого кандидата проверяются; заблокированный baseline не позволяет
пропустить проверку чисел или структуры более позднего кандидата.

## Результат и блокировки

Результат имеет `format: "tli-combat-upgrade-report-v1"`, `price_source: "caller"`
и `quantity_scope: "conditional_combat_dps"`. Он содержит полный `baseline`,
валюту, кандидатов, `ranking` и отделённую копию входного `scenario`.
Верхний `status` и `gaps` относятся к baseline; статус и gaps каждой замены
показываются отдельно. Наличие неизвестного кандидата не делает известный baseline
заблокированным.

Строка кандидата содержит только поля этого контракта:

| Поле | Значение |
| --- | --- |
| `id`, `name`, `cost` | Идентичность и цена вызывающей стороны |
| `dps` | Полный условный DPS собственного `result` |
| `delta` | `candidate.dps - baseline.dps` |
| `relative` | `delta / baseline.dps`; `null` при нулевом baseline |
| `per_cost` | `delta / cost`; `null` при нулевой или неизвестной цене |
| `status` | `blocked`, `not_upgrade`, `unpriced`, `free` или `upgrade` |
| `eligible_for_ranking` | Известный строго положительный `delta` |
| `eligible_for_cost_ranking` | Положительный `delta` и известная цена |
| `gaps` | Объединение gaps baseline и кандидата без повторов |
| `result` | Полный вложенный результат `rawcombat.evaluate` |

`candidate.missing` добавляется к копии `scenario.missing` перед расчётом: полная
цифра кандидата блокируется, а не вычитается из частичной модели. При gaps baseline
или кандидата `delta`, `relative`, `per_cost` равны `null`, оба eligibility-флага
ложны, `status` равен `blocked`. Если заблокирован только baseline, независимый
условный результат кандидата может сохранить собственный `dps`; сравнение остаётся
заблокированным. Вложенные traces и сценарии сохраняются без повторного расчёта
crit, casts или защитных множителей.

При известном `delta <= 0` статус — `not_upgrade`. При положительном delta
неизвестная цена даёт `unpriced`, нулевая — `free`, положительная — `upgrade`.
`ranking` содержит только ID с `eligible_for_cost_ranking: true`: сначала бесплатные
по ID, затем платные по убыванию `per_cost`, по меньшей цене и по ID. Бесплатным
вариантам не назначается бесконечная эффективность; варианты с неизвестной ценой
не попадают в ценовой рейтинг. Рейтинг условного сценария не является рекомендацией
покупки или подтверждением рыночной цены.

Не представимые конечным числом отношения и исчезновение ненулевого отношения
в ноль вызывают контролируемый `ValueError`. Никаких epsilon, Infinity или
автоматического ограничения результатов нет. Ошибки не включают payload кандидата.
Сценарии и вложенные результаты отделены от входа и друг от друга.

## Независимые числовые проверки

Синтетический spell даёт `100 × (1 + 0.25 × (3 - 1)) × 2 = 300` DPS одного
кастера. Topology с двумя присоединёнными кастерами, тремя попаданиями и retention
`0.25` даёт `2 × (1 + 2 × 0.25) = 3`. Cold factor равен `1 - 0.4 + 0.1 = 0.7`.
При armor `100000`, effectiveness `0.5`, penetration `0.1` и явном порядке
`after_effectiveness` итоговая mitigation — `0.8 × 0.5 - 0.1 = 0.3`, factor — `0.7`.
Increased taken `0.2`, отдельный more taken `0.1` и uptime `0.5` дают:

```text
baseline = 300 × 3 × 0.7 × 0.7 × 1.2 × 1.1 × 0.5 = 291.06
hit replacement (base 200): 582.12; delta = 291.06
topology replacement (three attached): 436.59; delta = 145.53
```

Это проверяет применение armour, penetration и taken ровно один раз.
Полный вымышленный пример запускается командой `python -m examples.compare_raw_combat`:
он сохраняет в JSON выводе сценарий, traces, явные цены 17/11 synthetic tokens
и рейтинг `hit`, затем `topology`. Это демонстрационные цены, не рыночные данные.
Отдельная проверка с двумя кастерами сохраняет по 30 casts/s каждому:
`100 × 30 × 2 = 6000`, без повторного глобального cap. Все примеры — искусственные
данные, не реконструкция текущего персонажа.

## Локальный отчёт сравнения

Для просмотра JSON и самостоятельного HTML выполните из корня проекта:

```powershell
python -m damage_lab combat-upgrades --scenario examples/combat_upgrades.json --output local-reports/combat-upgrades-example
```

Команда читает один сценарий не больше 8 MiB и создаёт новый каталог с
`comparison.json` и `index.html`. Каталог результата должен отсутствовать;
существующие отчёты и входной файл не перезаписываются. Дублирующиеся JSON fields,
нечисловые константы и неполные структуры отклоняются до публикации результата.

HTML показывает общую цель и uptime, baseline, кандидатов, явные цены, рейтинг,
пробелы и трассу. Blocked сценарий остаётся допустимым диагностическим результатом:
неподтверждённый baseline или кандидат не получают выдуманной числовой дельты либо
рекомендации. Цены примера вымышлены; автоматического рынка и resolver замен вещей
команда не добавляет.

## Нужный прирост в пределах бюджета

`damage_lab.upgradegoal.evaluate(document, minimum=100, budget=30)` выполняет то же
полное сравнение и добавляет `goal`: самый дешёвый подходящий вариант из переданных
кандидатов. Существующий рейтинг эффективности `ranking` сохраняется. Отдельный
`goal.ranking` сортируется по цене, затем по убыванию прироста и по ID.

Для CLI оба необязательных флага задаются вместе:

```powershell
python -m damage_lab combat-upgrades --scenario examples/combat_upgrades.json --output local-reports/combat-upgrades-goal-example --minimum-gain 100 --budget 30
```

Без этих флагов формат и поведение обычного сравнения остаются прежними, без `goal`.
Минимальный прирост должен быть конечным положительным числом, бюджет — конечным
неотрицательным. Повтор флага, NaN/Infinity, переполнение и исчезновение ненулевого
числа в ноль, например `1e-400`, отклоняются до публикации. Бесплатный поддержанный
вариант может пройти при бюджете `0`.

В отбор входят только поддержанные положительные приросты с явной ценой,
достигающие минимума и не превышающие бюджет. Неизвестные эффекты, effective level,
пулы либо цена не заполняются предположениями. Цена и валюта остаются данными
вызывающей стороны, без конвертации или проверки рынка. Например, при baseline
`1000` вариант `1500` за `100` эффективнее по gain/cost, чем `1100` за `25`; но для
прироста хотя бы `100` и бюджета `30` выбран второй.

JSON содержит `goal` формата `tli-combat-upgrade-goal-v1` с полями `minimum_gain`,
`budget`, `currency`, `quantity_scope: "conditional_combat_dps"`, `ranking`,
`selected`, `status` и `excluded: [{id, reasons}]`. Статус — `selected`, `blocked`
либо `no_supported_affordable_candidate`; при отсутствии выбора `selected: null`.
Причины исключения: `blocked`, `unpriced`, `not_upgrade`, `below_minimum`,
`over_budget`; защитная проверка также может вернуть `ineligible`.
JSON и HTML показывают причины; HTML добавляет секцию `upgrade-goal` и имя
выбранного варианта в `goal-selected`, когда выбор есть.

Параметры цели сохраняются в каноническом числовом виде: `100`, `100.0` и `1e2`
дают одинаковую цель, целый бюджет выше `2**53` не округляется через float,
`-0.0` бюджета становится `0`. Нецелые float сохраняют свою доступную точность.
HTML повторно вычисляет производные поля из сценария и указанных в отчёте
параметров цели; это проверка согласованности, без криптографического подтверждения
происхождения. Выбор относится только к переданным кандидатам и условной модели:
он не доказывает оптимальность на всём рынке, точный текущий DPS Carino или полноту
автоматического импорта.
