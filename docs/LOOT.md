# Условный расчёт ожидаемого дропа

`damage_lab.loot` считает ожидаемое число **слотов дропа или наборов предметов** для явно нормализованного сценария. Это отдельная библиотека: она не меняет DPS, не импортирует модификаторы персонажа и не восстанавливает отсутствующие базовые шансы. Дробный результат — математическое ожидание, а не предсказание фактического количества предметов.

Правила взяты из Help в TLIDB, проверенного 2026-10-21 для проекта SS14. Это неофициальное зеркало; релизная применимость каждого старого абзаца не подтверждена. Подробности и противоречия сохранены в [исследовании](research/help-loot-formulas.md).

## Чистые функции

```python
from damage_lab import loot

loot.quantity(3, ordinary=[0.25, 0.5], additional=[0.5, 1], typed=[0.25, 0.75],
              eligible={"general": True, "type": True})["expected"]  # 31.5

loot.conversion({"gear": 7.5}, chances={"gear": {"fuel": 1, "ember": 0.5}})["expected"]
# {"gear": 0.0, "fuel": 5.0, "ember": 2.5}

loot.replication({"fuel": 2.5}, ordinary={"fuel": [2, 3]}, additional={"fuel": [1, 2]})["expected"]
# {"fuel": 60.0}
```

Все функции возвращают `status="conditional_expectation"`, результат и `trace` со ссылкой на правило каждой стадии.

| Функция | Обязательный контракт |
| --- | --- |
| `quantity` | Один исходный тип; `ordinary`, `additional`, `typed` — явные списки долей; `eligible` содержит ровно два boolean: `general`, `type` |
| `conversion` | Словарь исходных ожиданий и ровно такие же исходные ключи в `chances`; `{}` явно обозначает отсутствие конверсии; каждый шанс в диапазоне 0–1 |
| `replication` | Для каждого результирующего типа обязательны оба словаря классов; `[]` явно обозначает отсутствие копий; значения — гарантированные неотрицательные целые числа |
| `scenario` | Полный документ следующего формата; неизвестные поля и неполные правила отвергаются |

[Quantity](https://tlidb.com/en/Drop_quantity#DropquantityManualRule) применяет общий additive pool и отдельные additional factors. [Типовой pool](https://tlidb.com/en/Drop_Quantity_Bonuses_for_Certain_Item_Types) складывается. Отрицательные обычные и типовые бонусы допустимы, пока сумма не создаёт отрицательный factor; каждый additional factor также неотрицателен. Даже проигнорированные области валидируются и остаются в trace.

[Конверсия](https://tlidb.com/en/Type_Conversion) нормирует competing probabilities при сумме выше 1. При меньшей сумме остаток сохраняет исходный тип — явное вероятностное продолжение описанного правила. Все исходные типы обрабатываются одновременно, без каскада и повторного применения destination quantity. Сохраняется ожидаемое число слотов/наборов, **не** неизвестное число единиц внутри набора. Нулевые исходные типы остаются в результате и требуют явных replication pools.

[Дополнительные предметы](https://tlidb.com/en/Additional_Drops) добавляются после quantity, затем доступны конверсии и [гарантированной репликации](https://tlidb.com/en/Replicate#ReplicateManualRule). Вход `expected` для дополнительного дропа уже должен учитывать точный шанс и число подходящих триггеров; `eligible` обязателен и не выводится из типа монстра. Случайные replication chances сейчас не поддержаны. [Общий порядок](https://tlidb.com/en/Effect_Priority) указан в trace.

## Сценарий и CLI

Сохраните этот синтетический пример в `scenario.json`:

```json
{
  "format": "tli-loot-scenario-v1",
  "base": [
    {
      "type": "gear",
      "expected": 2,
      "ordinary": [1],
      "additional": [0.5],
      "typed": [1],
      "eligible": {"general": true, "type": true}
    }
  ],
  "extra": [{"type": "gear", "expected": 0.5, "eligible": true}],
  "conversion": {"gear": {"fuel": 1}},
  "replication": {
    "ordinary": {"gear": [], "fuel": [1]},
    "additional": {"gear": [], "fuel": [2]}
  }
}
```

```powershell
python -m damage_lab.loot --input scenario.json --output loot-result
```

Ожидаемый результат — `gear: 0`, `fuel: 75`: базовые 12 слотов плюс 0.5 дополнительного слота, конверсия, затем 6 копий. Существующий `loot-result` отвергается; родительская папка должна существовать. На Windows готовый `report.json` публикуется переименованием временной папки. Ошибки входа не создают итоговую папку. Дубли полей JSON запрещены.

Внутри функций арифметика использует точные отношения входных чисел; JSON-доли сначала читаются как Decimal. Числа результата сериализуются в конечные float. Переполнение и исчезновение ненулевого результата до нуля вызывают ошибку, а не скрытое округление.

Модель не рассчитывает rarity probabilities, состав таблиц, содержимое конвертируемых наборов, цены наград, доход за карту или универсальное распределение случайного округления. Эти ограничения присутствуют в отчёте. Названия типов являются явными метками сценария; их соответствие игровым категориям должен подтвердить источник нормализованного входа.
